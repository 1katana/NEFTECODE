# ГЕРА — 24-2000 / гидроочистка

<aside>
🧪

**Цель исследования:** понять, какие режимные параметры установки 24-2000 связаны с качеством гидроочищенного дизельного топлива и какие из них потенциально можно использовать как управляющие воздействия в what-if / Optimizer.

Главная связь для проверки: **режим 24-2000 → технологический лаг → содержание серы / другие показатели качества → ЛИМС-контроль**.

</aside>

## 1. Зачем нам отдельно разбирать 24-2000

В общей цепочке задачи рассматривается **АВТ → гидроочистка 24-2000 → блендинг → товарное дизельное топливо**. АВТ формирует промежуточные фракции, а участок 24-2000 находится непосредственно рядом с задачей очистки дизельного топлива от серы.

Поэтому телеметрия 24-2000 нужна не как ещё один набор признаков, а как описание режима, который модель должна связать с последующим качеством продукта.

> **Рабочая гипотеза:** изменения расхода сырья, реакторных температур/давлений, подачи водородсодержащего газа, квенча и параметров стабилизации могут менять качество гидроочищенного ДТ с некоторым временным лагом. Причинность по истории заранее не предполагаем — её нужно проверять на данных.
> 

## 2. Какие источники связываем

| Источник | Что даёт | Роль в модели |
| --- | --- | --- |
| **`242000_tags.csv`** | 10-минутная телеметрия установки 24-2000 | STATE + кандидаты в CONTROL |

| **ЛИМС** | Редкие лабораторные пробы | Ground truth / target для ML |
| **КИП + схемы** | Физический смысл сигналов и расположение в процессе | Интерпретация и подтверждение CONTROL |

</aside>

## 3. Что реально есть в справочнике 24-2000

На листе **КИП** справочника для 24-2000 описано **26 сигналов**. Важная особенность: короткое имя тега не гарантирует физический тип величины. Например, `T11` по справочнику — **массовый расход сырья**, а `P8` — **температура ГСС на входе Р-202**. Поэтому ориентируемся на текстовое описание, а не на букву `T/P/F`.

### Реакторный / гидроочистительный блок

| --- | --- | --- |
| `P3` | Сепаратор С-201. Давление на входе | STATE |
| `T5` | Реактор Р-201. Температура ГСС на выходе | STATE |
| `P8` | Реактор Р-202. Температура ГСС на входе | STATE / кандидат режима |
| `W10` | Реактор Р-202. Перепад давления | STATE / reliability |

| `F15` | Расход квенча в реактор Р-202 | кандидат CONTROL |
| `F19` | Реактор Р-202. Давление на входе | STATE / кандидат режима |

## 4. Что из этого может быть важно для серы

Сначала проверяем не «все 26 тегов против серы», а несколько физических групп.

### 1. Нагрузка установки

- массовый/объёмный расход сырья: `T11`, `F26`;
- выпуск гидроочищенного ДТ: `F17`, `T23`;
- изменение нагрузки как отдельный признак: `Δfeed`, rolling slope.

### 2. Реакторный режим

- температуры ГСС: `T5`, `P8`;
- давление / перепад давления: `P3`, `F19`, `W10`;
- свежий ВСГ: `P24`;
- квенч: `F15`.

### 3. Стабилизация

`F9`, `Q21`, `F14`, `T16`, `T18`, `Q20`, `W4` — могут быть полезны как признаки последующего состояния продукта, но сначала надо отделить реакторную часть от параметров стабилизации и не смешивать их физический смысл.

### 4. Оперативное качество

`T6`, `W7`, `P13`, `F25` рассматриваем как **ПАК/ВАК-признаки**, а не как лабораторный target. Для обучения целевой серы используем реальную пробу ЛИМС; оперативные анализаторы помогают понять состояние между пробами.

## 5. STATE / CONTROL / TARGET — предварительное разделение

<aside>
🛑

**CONTROL пока не фиксируем окончательно.** По спецификации Optimizer имеет право менять только параметры, подтверждённые как реальные setpoint / управляющие воздействия по актуальной КИП и технологической документации. Исторический min/max не является промышленным пределом.

</aside>

| Класс | Что сюда относим сейчас | Статус |
| --- | --- | --- |
| **STATE** | температуры, давления, ΔP, расходы, выпуск, параметры стабилизации | можно использовать как наблюдаемые признаки |
| **CONTROL candidates** | `T11/F26` feed, `F15` quench, `P24` свежий ВСГ, отдельные подтверждённые режимные setpoint | нужна ручная верификация |
| **TARGET** | сера ЛИМС; далее T95 / flash point / D15 по выбранным моделям | target = только реальный лабораторный замер |
| **LIMIT** | S ≤ 10 мг/кг + технологические/model bounds | проверяет Safety до ranking |

## 6. Как проводить EDA 24-2000

### Шаг 1. Проверить сам временной ряд

- диапазон дат и шаг времени;
- пропуски и повторные timestamp;
- flatline / stale;
- резкие скачки и выбросы;
- каналы с подозрительно постоянными кодоподобными значениями;
- согласованность пар, которые описывают близкие величины (`T11` ↔ `F26`, `F9` ↔ `Q21`, `F17` ↔ `T23`).

### Шаг 2. Найти реальные изменения режима

Для shortlist-параметров строим `Δ`, rolling mean/std/slope и ищем периоды:

```
feed ↑ / ↓
температура реактора ↑ / ↓
давление / ΔP изменилось
ВСГ ↑ / ↓
квенч ↑ / ↓
```

Нужно выбрать **3–5 хорошо различимых timestamp / интервалов** и передать их в общий анализ ЛИМС + ПАК + телеметрии.

### Шаг 3. Проверить отложенный отклик качества

Для каждого события режима смотрим, что происходит с:

- `T6 / W7 / P13` — оперативной серой;
- ПАК по сере из отдельной выгрузки;
- следующими реальными ЛИМС-пробами серы.

Не фиксируем один лаг заранее. Проверяем кандидаты, например **30 мин / 1 ч / 2 ч / 4 ч / 6 ч**, а затем выбираем по train/validation без подглядывания в test.

### Шаг 4. Сформировать признаки для ML

Для каждой лабораторной пробы ЛИМС:

```
telemetry(t <= sample_time)
lags
rolling mean / std / min / max / slope
latest PAK/VAK + age
previous LIMS + age (если допускаем экспериментом)
missing / stale / outlier / filled masks
```

**Одна лабораторная проба = одна target-строка.** Протянутые на 10-минутную сетку значения ЛИМС не считаются новыми независимыми целями.

## 7. Что нельзя делать

- Не считать, что `T*` всегда температура, `P*` всегда давление, а `F*` всегда расход.
- Не считать все измеряемые теги управляющими.
- Не использовать ПАК/ВАК как единый target вместе с ЛИМС.
- Не брать значения телеметрии после времени отбора лабораторной пробы.
- Не удалять автоматически редкий тяжёлый режим как «outlier».
- Не выдавать исторические min/max за безопасные технологические границы.
- Не делать случайный shuffle train/test для временных рядов.

## 8. Что должно получиться на выходе исследования Геры

| Результат | Что передать команде |
| --- | --- |
| **Карта тегов 24-2000** | тег → физический смысл → блок процесса → STATE / CONTROL candidate / quality |
| **Data quality** | missing, stale, outlier, подозрительные каналы, дублирующие сигналы |
| **Shortlist признаков** | feed, reactor T/P/ΔP, ВСГ, quench, stabilization, product flow |
| **3–5 режимных событий** | timestamp + что изменилось + какие сигналы подтвердили изменение |
| **Lag hypotheses** | какие задержки проверить для связи режим → ПАК → ЛИМС |
| **CONTROL shortlist** | только кандидаты, отдельно отметить что подтверждено / не подтверждено |

## 9. Главный вопрос

> **Есть ли в истории достаточно изменений режима, чтобы учиться на их последствиях?**
> 

На уровне структуры данных — **да, нужные группы сигналов присутствуют**: нагрузка, реакторные температуры/давления, перепад давления, свежий ВСГ, квенч, стабилизация и оперативные сигналы качества.

Но окончательный ответ требует статистики самого `242000_tags.csv`: вариативности каналов, количества смен режимов, длительности стабильных участков и покрытия качеством. **В доступном сейчас пакете этого CSV нет, поэтому конкретные 3–5 timestamp здесь намеренно не выдуманы.** После получения файла этот раздел можно закрыть первым EDA-проходом.

## Итог для общей архитектуры

```
24-2000 telemetry
        ↓
ProcessState + lag features
        ↓
QualityAgent: прогноз S / P(S > 10)
ReliabilityAgent: тяжесть режима / ΔP / data quality
        ↓
Candidate Generator: только подтверждённые CONTROL
        ↓
Safety: hard constraints
        ↓
Optimizer → Orchestrator → объяснимая рекомендация
```

**Ключевой принцип:** 24-2000 даёт нам не готовый ответ «что менять», а наблюдаемую историю режима. Что именно можно изменять, определяется отдельным `control_config`; эффект изменения оценивает модель, а небезопасные сценарии отбрасываются до оптимизации.
