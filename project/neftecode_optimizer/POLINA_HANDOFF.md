# Блок оптимизации — передача Полине

Это описание блока Никиты для сборки общего Python-пайплайна. Блок уже можно
подключить к оркестратору и прогнать на синтетических данных. **Он пока не готов
выдавать реальные производственные рекомендации:** в основном конфиге нет
подтверждённых управляющих параметров, а реальные модели качества и надёжности
ещё должны быть подключены. Демонстрационный результат — не команда оператору.

## Архитектура и ответственность

В актуальной договорённости команды **три агента**: Гера делает
`QualityAgent`, Ислам — `ReliabilityAgent`, Полина — `Orchestrator`.
Часть Никиты — не один класс `Optimizer`, а весь **алгоритмический контур
выбора действия**:

| Блок Никиты | Что выдаёт |
| --- | --- |
| `control_config` + Candidate Generator | Разрешённые CONTROL и список вариантов действий, включая KEEP. |
| Safety Layer | Допуск/отклонение варианта с конкретными причинами; жёсткие ограничения нельзя перекрыть баллом. |
| Optimizer / Ranking | Отсортированный shortlist безопасных сценариев, лучший вариант или `NO_FEASIBLE_SOLUTION`. |
| Контракты, моки, тесты | Стабильный Python-интерфейс, чтобы Полина могла собрать сквозной запуск ещё до появления реальных моделей. |

Это **разные логические компоненты**, хотя `Optimizer.search()` сейчас собирает
их вызовы в одну удобную точку входа. Никита не обучает модель качества Геры,
не реализует агент надёжности Ислама и не принимает финальное решение
`REFUSE` за Полину. В экспорте Notion есть противоречивые таблицы с
распределением имён; здесь зафиксировано распределение, которое Никита
подтвердил для команды.

## Что делает блок

Оптимизатор получает наблюдаемое состояние процесса, создаёт ограниченный набор
вариантов изменения разрешённых управляющих параметров (CONTROL) и всегда
добавляет вариант **KEEP** — ничего не менять. Для каждого варианта запрашивает
прогноз качества у агента Геры и риск надёжности у агента Ислама. До и после
вызова агентов отсеивает варианты по жёстким ограничениям; оставшиеся
ранжирует. Возвращает лучший вариант, причины отбраковки и предупреждения.
Физическую модель процесса, контрфактические признаки и финальное решение
«показать оператору / отказать» этот блок не заменяет.

Сейчас действует жёсткий предел серы **10 мг/кг для товарного дизеля после
блендинга**. Оценка серы только после гидроочистки этому требованию не
равнозначна. Safety не разрешает компенсировать нарушение качества или
критический риск надёжности выгодой по экономике.

| Офлайн-адаптер | Читает архив с историческими строками, отдаёт `HISTORICAL`-состояние без лабораторного target во входе агентов. Это проверка проводки данных, не доказательство эффекта изменения режима. Сам датасет в передаваемый архив не входит. | `optimization/historical_data.py` |
| Проверка и передача | Автотесты на перебор, ограничения, ошибки агентов и демо; сборка переносимого ZIP только из выбранных исходников и документации. | `tests/`, `scripts/build_handoff.py`, `pyproject.toml` |

Реальных моделей качества/надёжности, поставщика живых данных и финального
операторского решения в этом пакете **нет**: они принадлежат Гере, Исламу и
Полине соответственно. Незаполненные настройки и правила перечислены ниже
отдельно; наличие файла YAML не означает, что диапазоны уже согласованы.

## Как встроить в общий пайплайн

```text
Источники данных → Полина: сборка ProcessState, происхождение и время данных
              → Никита: генерация кандидатов
              → Safety до прогнозов
              → Гера.predict(state, candidate) + Ислам.evaluate(state, candidate)
              → Safety после прогнозов → ранжирование
              → OptimizationResult → Полина: финальный допуск/REFUSE и вывод
```

Все блоки можно держать в одном Python-проекте и вызывать как обычные объекты,
без HTTP. Минимальная точка интеграции:

```python
from optimization import Optimizer, ProcessState, load_safety_policy

state = ProcessState.model_validate(payload_from_orchestrator)
optimizer = Optimizer(
    quality_agent=quality_agent,
    reliability_agent=reliability_agent,
    control_config="optimization/control_config.yaml",
    safety_policy=load_safety_policy("optimization/safety_policy.yaml"),
)
result = optimizer.search(state)
```

Полина может передать словарь: `ProcessState` проверит `source`,
`timestamp`, `values` (числа или `None`) и `metadata`. Источник указывать
явно: `SYNTHETIC` для генератора, `HISTORICAL` для архива, `LIVE` только для
действительно оперативного потока. Для состояния, привязанного к ЛИМС,
`timestamp` — **время забора пробы**, не время готовности результата. При
историческом воспроизведении нельзя подмешивать результат, который на момент
решения ещё не был доступен; нужен отдельный учёт времени его появления.
Оптимизатор не определяет свежесть измерений автоматически. Если
`metadata["telemetry_available"]` передан и не равен `True`, Safety отклонит
кандидатов.

Гера предоставляет `predict(state, candidate) -> QualityAssessment | dict`:
прогноз серы товарного дизеля в мг/кг, нижнюю/верхнюю границы, вероятность
нарушения, уверенность, `product=COMMERCIAL_DIESEL`,
`source=REAL`, версию модели. Ислам предоставляет
`evaluate(state, candidate) -> ReliabilityAssessment | dict`: класс риска
(`CRITICAL` обязательно выставляется явно), `risk_score` от 0 до 1,
уверенность, `source=REAL`, версию модели. Для изменения CONTROL по умолчанию
обе оценки должны быть реальными. Оптимизатор отдаёт агентам независимые копии
состояния и кандидата; `changes` содержит новые абсолютные значения уставок,
`deltas` — отклонения от текущих. Лаги, rolling-признаки и последствия
изменения уставки считают соответствующие агенты, не оптимизатор.

Результат имеет статус `RECOMMEND`, `KEEP` или
`NO_FEASIBLE_SOLUTION`. В нём есть `best_candidate`,
`ranked_candidates`, `rejected_candidates`, `agent_failures`,
`reasons`, `warnings`, `input_source`, `uses_mock_assessments`,
`search_truncated`. У элементов `ranked_candidates` есть порядковый `rank`
(1 = лучший); `score` остаётся null, поскольку для лексикографического выбора
нет согласованной скалярной формулы. Ошибка отдельного агента исключает конкретный вариант,
но не обрывает весь перебор. `RECOMMEND` означает лучший найденный вариант
**среди проверенных кандидатов**, а не разрешение на физическое управление.
Финальный допуск и отображение оператору — ответственность оркестратора.

## Что необходимо заполнить или согласовать

| Где / чей блок | Что именно требуется | Сейчас и последствие |
| --- | --- | --- |
| Никита + технолог: `optimization/control_config.yaml` | Утвердить промышленные `min/max/step/max_delta` для сопоставленных `T6/F9/P13` и модельных controls блендинга. | Теги подтверждены, но диапазоны пока `EXPERIMENTAL_MODEL`; это не операторный регламент. |
| Гера + Ислам → Никита: `optimization/safety_policy.yaml` | Проверить обязательные входы и численные области применимости по будущему live-потоку. | Поля заполнены для текущей модели качества; ReliabilityAgent всё ещё требует отдельной валидации. |
| Гера: реальный агент качества | Откалибровать candidate-response и заменить модельные рецептуры реальными, если они появятся. | Товарный продукт уже рассчитывается линейным блендингом, но это явно маркированная модельная оценка. |
| Ислам: реальный агент надёжности | Реализовать оценку риска каждого контрфактического сценария; согласовать смысл `risk_score`, уровней риска и признаки для `CRITICAL`. | Без реальной оценки изменение CONTROL по основной policy не допускается. |
| Полина: поставщик состояния и оркестратор | Сохранять приоритет источников и реальный признак публикации ЛИМС, когда он появится; разделять demo/live и показывать причины отказа. | Сейчас действует консервативная доступность `sample + 4h`; `LIVE` нельзя выставлять для синтетики или офлайн-данных. |
| Никита + команда: дополнительные технологические правила | Подтвердить оставшиеся паспортные показатели, если они нужны. | Уже проверяются сера, T95, сезонные плотность/ЦЧ, 100% долей и присадка до 3%. |
| Команда: необязательные решения | Нужен ли порог `max_violation_probability`, другие запрещённые уровни риска/уверенности и экономическая формула. Если экономика нужна, подключить `economic_evaluator(state, candidate) -> float` с сопоставимым значением для **всех** безопасных вариантов, включая KEEP. | Числового порога и формулы в исходных данных нет: `max_violation_probability: null`, экономика отключена. Без формулы ранжирование всё равно работает; экономический показатель не отменяет Safety. |
| Полина + Никита: выпуск рекомендаций | Утвердить финальные правила отображения: не выводить как боевую рекомендацию результат с `input_source != LIVE`, `uses_mock_assessments=true`, `RELAXED_ACTION_POLICY`, неполными обязательными настройками или иной значимой ошибкой/предупреждением. | Основная policy запрещает действия на non-live и не-REAL оценках, но решение о публикации и `REFUSE` остаётся у Полины. |

## Переключатели: демо и реальный контур

Флаги лежат в `optimization/safety_policy.yaml` или в отдельной policy для
демо; тип CONTROL (`basis`) задаётся в `control_config.yaml`. Само по себе
переключение policy **не превращает синтетические данные в реальные**.

| Режим | Вход / CONTROL / агенты | Какую policy использовать |
| --- | --- | --- |
| Сквозное демо | `SYNTHETIC` / `MOCK_FIXTURE` / ответы `MOCK` | Только `examples/mock_control_config.yaml` вместе с `examples/mock_safety_policy.yaml`. В последней включены **все три** разрешения: `allow_mock_controls`, `allow_non_live_actions`, `allow_unverified_assessments_for_actions`. Полученный `RECOMMEND` — только демонстрация. |
| Целевой реальный режим, после согласования | `LIVE` / подтверждённые `CONFIRMED_OPERATING` / ответы обоих агентов `REAL` | Основные YAML после заполнения CONTROL, обязательных признаков и model bounds; `reject_mock_assessments: true`, все `allow_*` ниже — `false`. Оркестратор всё равно отдельно решает, можно ли показать результат оператору. |
| Исследовательский модельный режим | Явно помеченные `EXPERIMENTAL_MODEL`-диапазоны | Отдельный согласованный конфиг и `allow_experimental_controls: true`. Это эксперимент, **не** подтверждённый эксплуатационный диапазон. |

| Поле SafetyPolicy | Что переключает / важная оговорка |
| --- | --- |
| `allow_mock_controls` (по умолчанию `false`) | Разрешает изменение только CONTROL с `basis: MOCK_FIXTURE`; одного этого флага для демо на синтетике и моках недостаточно. |
| `allow_non_live_actions` (`false`) | Разрешает изменяющий кандидат на `SYNTHETIC`/`HISTORICAL`; без него может пройти KEEP, но не действие. Не ставить в боевую policy. |
| `allow_unverified_assessments_for_actions` (`false`) | Разрешает действие, даже если ответ Геры или Ислама не помечен `source: REAL`. Не делает оценки достоверными. |
| `allow_experimental_controls` (`false`) | Разрешает изменение CONTROL с `basis: EXPERIMENTAL_MODEL`; требует отдельного решения команды, не заменяет `CONFIRMED_OPERATING`. |
| `reject_mock_assessments` (в основном YAML пока `false`) | При `true` отбрасывает ответы `source: MOCK` даже для KEEP. При текущем `false` изменение CONTROL всё равно требует два `REAL`, если не включён предыдущий флаг. Для боевого режима согласовать `true`. |
| `use_prediction_upper` (`true`) | При `true` сравнивает с лимитом верхнюю границу прогноза; при `false` — точечный прогноз. **Обе границы интервала всё равно обязательны** по текущему контракту Safety. |
| `max_violation_probability` (`null`) | `null` — нет жёсткого вероятностного порога, но вероятность обязательна и участвует в ranking; число 0–1 задавать только после согласования. |
| `rejected_confidences` (`[LOW]`) | Какие уровни уверенности считаются недопустимыми; текущий список — осторожный выбор реализации, а не число из ТЗ. |
| `rejected_reliability_risks` (`[CRITICAL]`) | Запрещённые классы риска; `CRITICAL` нельзя убрать из списка. |
| `sulfur_limit_mg_kg` (`10`) | Жёсткий лимит для товарного дизеля; можно ужесточить, но не поднять выше 10 мг/кг. |
| `required_inputs`, `model_bounds` | Заполнены для `T6/F9/P13` и model-controls блендинга; требуют технологического утверждения перед production. |

Отдельно от YAML у `Optimizer` есть `max_candidates=100` (включая KEEP)
и `max_changed_controls=2`: они ограничивают время перебора, но могут отсечь
часть вариантов и дать `SEARCH_TRUNCATED`. Необязательный
`economic_evaluator` подключается Python-объектом, а не флагом; без
согласованной формулы он отсутствует. Даже с ним `score` остаётся null:
экономика участвует в лексикографическом сравнении, но общих весов для
скалярного балла нет. Любое включение
`allow_*` отмечается предупреждением `RELAXED_ACTION_POLICY`. Полина не
должна выпускать такой результат как боевую рекомендацию, даже если внутри
стоит статус `RECOMMEND`.

## Что уже можно передать и проверить

- Полине — этот контракт и пакет `optimization`; отдельные сервис, API и
  JSON Schema для сборки в одном Python-процессе не требуются.
- Гере и Исламу — типы `ProcessState`, `CandidateAction`,
  `QualityAssessment`, `ReliabilityAssessment` из `optimization/models.py`.
- Никите/технологу — запрос на подтверждённые CONTROL и границы; после их
  получения заполняются два основных YAML и дописываются согласованные правила.

Локально: `py -m pip install -e ".[dev]"`, затем `py -m pytest`.
Сквозное демо описано в [README.md](README.md), подробный контракт —
в [docs/integration.md](docs/integration.md), расхождения исходных материалов —
в [docs/source_evidence.md](docs/source_evidence.md). Исторический прогон
описан в [docs/dataset_replay.md](docs/dataset_replay.md): он проверяет
проводку и форму данных, **не** реальную эффективность воздействий.

## Как передать Полине

Из корня проекта запустить `py scripts/build_handoff.py` и отправить **только**
`handoff/neftecode_optimizer_for_polina.zip`. В нём лежат Python-пакет,
основные YAML, этот документ, инструкция, демо-файлы и самодостаточные тесты.
Исходных архивов, датасетов, PDF, Excel, виртуального окружения и сборочных
каталогов в ZIP нет. После распаковки Полина открывает каталог
`neftecode_optimizer`, устанавливает зависимости командой
`py -m pip install -e .` (для запуска тестов — `py -m pip install -e ".[dev]"`)
и импортирует `optimization` из своего оркестратора. Файл
`optimization/control_config.yaml` внутри передаваемого пакета остаётся
пустым до согласования реальных CONTROL — архив не делает блок «боевым».
