# Контракт блока Никиты

Весь блок работает в одном Python-процессе. Для подключения к оркестратору
достаточно импортов; HTTP-сервера и API нет.

## Вызов

```python
from optimization import Optimizer, ProcessState, load_safety_policy

optimizer = Optimizer(
    quality_agent=quality_agent,
    reliability_agent=reliability_agent,
    control_config="optimization/control_config.yaml",
    safety_policy=load_safety_policy("optimization/safety_policy.yaml"),
    max_candidates=100,
    max_changed_controls=2,
)
result = optimizer.search(process_state)
```

Числа 100 и 2 ограничивают вычислительный перебор, а не технологический режим.
Объекты агентов должны реализовать синхронные методы:

- Гера: `predict(state, candidate) -> QualityAssessment | dict`.
- Ислам: `evaluate(state, candidate) -> ReliabilityAssessment | dict`.

Агенты получают исходное состояние и предложение отдельно. `changes` содержит
абсолютные новые значения, `deltas` — разности относительно исходных значений.
Построение контрфактических признаков и прогноз последствий принадлежат агентам.
Оптимизатор не пересчитывает физические зависимости, лаги или rolling-признаки.
Каждому агенту передаются независимые глубокие копии входов.

## Данные

`ProcessState.values` — отображение имён признаков в числа или `None`.
NaN и Infinity отклоняются; отсутствующие значения не заполняются.
На внешней границе разрешается передать словарь вместо ProcessState.
`ProcessState.source` обязателен: `SYNTHETIC` для генератора Полины,
`HISTORICAL` для офлайн-проверки, `LIVE` для будущего реального источника.
Оптимизатор не угадывает источник по числам или `metadata`.
Для LIMS `timestamp` обозначает время забора пробы. Это не означает, что результат
анализа был доступен в этот момент: доступность результатов при историческом
воспроизведении обеспечивает поставщик состояния.
Для офлайн-проверки `iter_historical_cases` читает split-файлы из
`датасеты.zip`, отделяет лабораторный target от `ProcessState` и передаёт
только текущие режимные теги. Подробности и ограничения —
[dataset_replay.md](dataset_replay.md).

Прогноз качества сейчас относится только к сере, в мг/кг:
`quality_prediction`, `prediction_lower`, `prediction_upper`,
`violation_probability` (вероятность нарушения лимита),
`data_confidence` (HIGH/MEDIUM/LOW) и `product`.
`product` может быть `COMMERCIAL_DIESEL`, `HYDROTREATED_DIESEL` или `UNKNOWN`.
Лимит 10 мг/кг относится к товарному дизелю после блендинга. Поэтому Safety
отклоняет последние два значения с причиной
`QUALITY_PRODUCT_NOT_COMMERCIAL_DIESEL`. Если поле не передано, оно становится
`UNKNOWN` и также отклоняется. Агент Геры должен выдать прогноз товарного
продукта либо команда должна явно построить переход через блендинг.
Среднее должно лежать внутри интервала; все три значения обязательны для допуска.

Надёжность: `reliability_risk` (LOW/MEDIUM/HIGH/CRITICAL),
`risk_score` от 0 до 1, `data_confidence`, `warnings`.
Предупреждения сохраняются как текст; критичность не угадывается по словам.
Агент обязан передать критическое состояние через `reliability_risk=CRITICAL`.
По умолчанию блокируется CRITICAL; другие запрещённые уровни задаёт policy.

Оба агента могут передавать `source` и `model_version`.
Неуказанный источник — UNKNOWN. Встроенные моки всегда возвращают MOCK.
Поля, которых нет в контракте, считаются ошибкой ответа.
Для изменения CONTROL по умолчанию обе оценки должны иметь `source: REAL`.
Моковые/неизвестные оценки допускаются к действию только при явном
`allow_unverified_assessments_for_actions=true` в демонстрационной policy.

## Выбор

Генератор выдаёт KEEP, затем одиночные изменения и комбинации ±k·step
для целых k от 1 до допустимого по max_delta и min/max. Порядок внутри
CONTROL: -step, +step, -2·step, +2·step и так далее.
Порядок тегов лексикографический, внутри тега сначала уменьшение, затем увеличение.
Лимит включает KEEP. Если перебор усечён, `search_truncated=true`;
глобальная оптимальность по всей области управления не заявляется.

До вызова агентов проверяются обязательные входы, все настроенные CONTROL,
дельты, происхождение диапазона и заданные model bounds. KEEP проходит проверки
входов и границ, но не считается действием. Каждый CONTROL обязан иметь `basis`:
`CONFIRMED_OPERATING`, `EXPERIMENTAL_MODEL` или `MOCK_FIXTURE`. По умолчанию
изменения последних двух отклоняются; для отдельно согласованного
эксперимента разрешается `allow_experimental_controls=true`, а для тестового
примера — `allow_mock_controls=true`. В результате такие диапазоны отмечаются
`CONTROL_RANGES_NOT_OPERATIONAL`.
Изменение CONTROL на `SYNTHETIC` или `HISTORICAL` по умолчанию отклоняется
как `NON_LIVE_ACTION_NOT_ALLOWED`; для сквозного демо нужно явно включить
`allow_non_live_actions=true`. KEEP можно проверить на любом источнике.
Любое ослабление action-policy добавляет `RELAXED_ACTION_POLICY` в предупреждения.
После прогнозов проверяются качество, неопределённость, уверенность и надёжность.
Лимит серы можно ужесточить, но нельзя поднять выше 10 мг/кг;
запрет CRITICAL также нельзя выключить. Использование верхней границы прогноза
и запрет LOW confidence — осторожные настройки этого блока, не цифры из ТЗ.

Допущенные сценарии сравниваются последовательно:

1. Меньшая вероятность нарушения серы.
2. Меньший risk_score надёжности.
3. Больший экономический показатель, только если явно подключён.
4. Меньшая сумма `abs(delta) / max_delta`.
5. ID кандидата для воспроизводимости.

При одинаковых рисках и экономике KEEP выигрывает за счёт нулевого изменения.
Порог «значимого улучшения» не придуман: используется точное сравнение.
Экономический callback `economic_evaluator(state, candidate) -> float`
необязателен. Он должен возвращать сопоставимый показатель для всех сценариев,
включая KEEP. Формула, единицы и базовый режим определяются командой.
Без callback экономика отключена; NaN или сбой callback исключает сценарий.
Экономика не компенсирует нарушение ограничений и вызывается только после Safety.

## Результат и сбои

- `RECOMMEND`: лучший проверенный вариант меняет CONTROL.
- `KEEP`: лучший проверенный вариант — текущее состояние.
- `NO_FEASIBLE_SOLUTION`: среди рассмотренных вариантов нет полностью оценённого
  допустимого решения. Возможные причины — ограничения, данные или ошибки агентов.

Финальный REFUSE и представление пользователю формирует оркестратор Полины.
Он должен учитывать `input_source`, `uses_mock_assessments`, `warnings`
и усечение поиска. Результат `RECOMMEND` по синтетическому или историческому
входу допустим только как демонстрационный и не должен уходить оператору.
Mock-результат предназначен для интеграционного прогона.
Для запрета моков включается `reject_mock_assessments` в SafetyPolicy.

`ranked_candidates` содержит безопасные сценарии и компоненты ранжирования.
Поле `rank` — порядковое место (1 = лучший вариант). `score` остаётся null:
лексикографический выбор не задаёт единого численного балла без согласованных
весов; не следует трактовать `rank` как экономическую полезность.
`rejected_candidates` содержит причины отказа Safety; при отказе до прогнозов
quality/reliability равны null. `agent_failures` содержит ID, имя компонента
и тип ошибки; `reasons` объединяет причины исключения.
`selection_reason`, `generated_count`, `state_timestamp` описывают выбор.
`input_source` копируется из `ProcessState.source` без переинтерпретации.

Ошибка вызова или схемы ответа одного агента исключает соответствующий кандидат;
перебор продолжается. Ошибка самого входного состояния или конфигурации вызывает
ValidationError/ValueError. Синхронный вызов не прерывает зависший агент:
ограничение времени должно обеспечиваться реализацией агента или внешним запуском.

## Что подтверждено ZIP и чего ещё нет

Подробная сверка исходных материалов: [source_evidence.md](source_evidence.md).

- ТЗ подтверждает только жёсткий лимит 10 мг/кг для товарного дизеля,
  приоритет безопасности и возможность явно помеченных модельных диапазонов.
- Для реальных действий нужны подтверждённые управляющие сигналы и
  min/max/step/max_delta/unit либо согласованный экспериментальный сценарий.
- Гера и Ислам должны передать обязательные признаки и границы применимости
  своих моделей. Для серы нужен прогноз товарного продукта или согласованная
  модель влияния блендинга.
- Вероятностный порог и экономическая формула не обязательны по ТЗ:
  без первого вероятность участвует в ранжировании, без второго экономика
  отключена. Если команда хочет жёсткие дополнительные правила, их нужно
  согласовать отдельно.

Пустые настройки отражаются в warnings. Наличие рабочих моков не подтверждает
пригодность модели для технологических рекомендаций.
